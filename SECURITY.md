# Security Policy

## Supported versions

Until a later stable release, security fixes are applied to the latest `0.1.x` release line and the default development branch.

## Reporting a vulnerability

Do not open a public issue containing vulnerability details, credentials, user data, or an exploit. Use GitHub's private vulnerability reporting flow under the repository **Security** tab. Include:

- affected commit or version;
- affected API, Worker, Tool, or data boundary;
- minimal reproduction steps;
- expected and observed authorization behavior;
- whether secrets or cross-user data may have been exposed.

If private reporting is temporarily unavailable, contact the repository owner through the GitHub profile without including exploit details in a public message.

## v0.1.0 trust boundaries

The default Docker Compose profile is intended for local development and controlled UAT only.

- Local Sandbox is not strong isolation for hostile code.
- The default deployment is not a multi-tenant SaaS security boundary.
- Development credentials generated by `make bootstrap` must not be reused in production.
- Public network exposure requires an authenticated reverse proxy, TLS, explicit CORS, secret rotation, and a reviewed production identity profile.
- Production OIDC/OBO, KMS-backed secrets, strong Sandbox isolation, multi-AZ storage, and immutable audit sealing are target architecture and are not claimed by v0.1.0.

## Repository hygiene

Never commit:

- `.env` or deployment environment files;
- Provider, Search, MCP, database, or cloud credentials;
- SSH private keys;
- database backups;
- UAT evidence containing user or Provider data;
- Session Workspace or Artifact bytes from real users.

Run the working-tree and Git-history checks before release:

```bash
make check-secrets
./scripts/check_repository_secrets.sh --history
```

Any credential that ever entered Git history must be revoked and rotated even if the commit is later rewritten.
